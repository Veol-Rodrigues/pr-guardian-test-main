# PR Guardian — Technical Architecture Overview

## Summary
PR Guardian is a serverless, event-driven AI code-review system deployed entirely as a GitHub Action. It embeds an LLM into the developer workflow without operating any hosted infrastructure: the CI runner is the compute layer, GitHub's own APIs are the data and delivery layer, and Gemini is the reasoning layer.

This version reflects a deliberate product pivot, from a single "AI Code Reviewer" comment to a **Pull Request Command Center** built around a **Calm Engineering** philosophy: objective, specific, educational feedback delivered exactly where it's relevant, summarized by a single Merge Readiness Score — with no alarmist language anywhere in the pipeline.

## System Design
The system remains a linear, stateless pipeline: no database, no persistent process, no message queue. Each review is triggered by an event, completes in a single job, and posts its result back to the Pull Request itself. What has changed is *what* gets posted and *how it's delivered* — the pipeline now produces two coordinated outputs (inline suggestions and a root summary) from one aggregated analysis pass, rather than a single flat comment.

### End-to-End Flow
* **Event Ingestion:** A `pull_request` webhook (`opened`, `synchronize`, or `reopened`) is caught by GitHub Actions, which spins up an ephemeral Ubuntu runner.
* **Environment Preparation:** The workflow installs Python 3.10, `requests`, and `python-dotenv`, then loads two credentials: the auto-provisioned `GITHUB_TOKEN` and the user-provided `GEMINI_API_KEY`.
* **Metadata & Diff Retrieval:** `pr_reviewer.py` calls the GitHub REST API twice against the same PR endpoint — once with the default JSON `Accept` header (for title, head commit SHA, additions/deletions) and once with `application/vnd.github.v3.diff` (for the raw unified diff). The head SHA is required by the Review API to anchor inline comments to a specific commit.
* **Diff Segmentation:** The diff is split into per-file blocks. For each block, the script extracts the file path and parses every hunk header (`@@ -a,b +c,d @@`) to build the set of new-file line numbers that are actually part of the diff — the only lines GitHub will accept an inline review comment against. Deleted and binary files are excluded from commenting but still counted in the files-changed overview.
* **Intelligent Chunking:** File blocks are packed into chunks that respect file boundaries and stay under a configurable line threshold (2000 lines by default). A single file whose diff alone exceeds the threshold is isolated into its own chunk rather than being split mid-hunk, which would corrupt line-number tracking.
* **AI Analysis (per chunk):** Each chunk is sent to Gemini's `generateContent` endpoint with a prompt that fixes the Calm Engineering tone and constrains the response to a JSON array of `{file_path, line_number, category, message, suggested_fix}` objects. `category` is restricted to `Security Enhancement`, `Architectural Observation`, or `Merge Readiness Suggestion` — deliberately excluding alarmist vocabulary at the schema level, not just in prose instructions. A failed chunk is logged and skipped rather than aborting the run, so one bad chunk (a transient Gemini error, a malformed response) doesn't cost the whole review.
* **Aggregation & Validation:** Findings from all chunks are combined, then filtered against the per-file valid-line sets computed during diff segmentation. Findings that don't map onto a commentable line are dropped with a log message rather than sent to GitHub, where they would otherwise cause the entire review submission to fail.
* **Scoring:** The Merge Readiness Score is computed deterministically in Python from the validated findings — `100` minus a fixed per-category weight for each finding, floored at `0`. This is intentional: the number a developer anchors on is not left to LLM arithmetic, which can be inconsistent between runs. Estimated review time saved is likewise a deterministic heuristic based on the PR's changed-line count, not a model guess.
* **Narrative Generation:** A second, smaller Gemini call takes the PR title, the changed-file list, and the validated findings, and produces a short natural-language paragraph describing the architectural impact of the change. This call is text-only (no JSON constraint) since it's prose for direct display, and it explicitly does not compute or restate the score, to avoid the two numbers ever disagreeing.
* **Delivery:** Inline findings are formatted as `path` / `line` / `side: RIGHT` review comments, each including a `suggestion` Markdown block when a concrete fix was provided, so GitHub renders a one-click "Apply suggestion" button. The Command Center summary (score, time saved, files overview, narrative, and a findings-by-category breakdown) is set as the `body` of the same review object. A single `POST /pulls/{number}/reviews` call submits both together, so the developer sees one coherent review rather than a disconnected set of comments.

## Key Design Decisions
* **GitHub Actions instead of a hosted webhook server:** Unchanged from the original design and still the most important architectural choice — authentication is implicit via `GITHUB_TOKEN`, the runner is provisioned on demand, and compute cost is zero on public repos.
* **Migrating from Issue Comments to the Pull Request Review API:** The previous design posted a single Markdown comment via the Issues Comments API, which cannot anchor to a specific line. Moving to `POST /pulls/{number}/reviews` allows findings to be attached to exact `file_path` / `line_number` pairs, and lets one API call carry both the inline comments and a top-level review body — eliminating what would otherwise be two separate, unlinked posts.
* **Deterministic scoring, generative narrative:** The Merge Readiness Score and time-saved estimate are computed in plain Python from structured data, while only the free-text architectural summary is delegated to the LLM. This keeps the number a developer trusts most immune to LLM non-determinism, while still getting natural-language framing where it adds value.
* **Line-validity filtering as a safety layer:** Because GitHub rejects review submissions containing a comment on a non-diff line, and because LLM-reported line numbers are occasionally off, every finding is checked against a line set derived directly from the diff's own hunk headers before submission. Invalid findings are dropped and logged rather than crashing the run or silently corrupting the whole review payload.
* **File-boundary chunking instead of naive line-splitting:** Splitting a diff purely on the line-count threshold risks cutting a file's diff in half, which would break the model's ability to reason about a hunk and would misalign line-number tracking. Chunking is instead done by accumulating whole file blocks up to the threshold, isolating any single oversized file into its own chunk.
* **Resilient per-chunk failure handling:** A failed or malformed Gemini response for one chunk is caught, logged, and excluded from aggregation, rather than raising and terminating the whole workflow. A large PR with one problematic file still gets a review for everything else.
* **Calm Engineering as a schema-level constraint, not just a prompt suggestion:** The `category` field's allowed values were deliberately chosen (`Security Enhancement`, `Architectural Observation`, `Merge Readiness Suggestion`) so alarmist framing is structurally impossible in the output, rather than relying on the model to consistently avoid words like "critical" on its own.
* **Least-privilege permissions:** Unchanged — `contents: read` and `pull-requests: write`, nothing more. Submitting a review with inline comments requires the same `pull-requests: write` scope as the previous issue-comment approach, so no permission expansion was needed for this migration.

## Trade-offs and Known Limitations
* **Line-number dependence on diff parsing correctness.** The valid-line filter depends on correctly parsing unified diff hunk headers. Unusual diff formats (e.g., some merge-conflict-style diffs) could cause valid findings to be dropped defensively; the system is tuned to fail safe (drop) rather than fail loud (crash or submit an invalid line).
* **Chunk isolation can still hit context limits.** A single file whose diff alone exceeds the chunk threshold is still sent as one request; a genuinely enormous single-file diff could still exceed Gemini's context window. A future iteration could sub-chunk within a file by hunk groups, at the cost of losing whole-file context for the model.
* **Two Gemini calls per run (chunks + narrative) increase latency and cost slightly** compared to the single-call design. This is intentional: keeping the narrative call separate and prose-only keeps the JSON-constrained review calls simpler and avoids asking one call to both extract structured line-level findings and write flowing prose.
* **LLM non-determinism in findings.** Two runs on the same diff can still produce slightly different inline findings, even though the score's *arithmetic* is deterministic given whatever findings are returned. Teams relying on this for a strict merge gate should treat the score as a strong signal, not a guarantee.
* **Suggested fixes are single-snippet, not multi-line-aware in all cases.** The `suggestion` block replaces the exact line commented on; fixes that require changes spanning multiple lines are described in the message but may not always be fully expressible as a one-line click-to-commit suggestion.

## Business Value
For a small-to-mid-sized engineering team, PR Guardian provides the equivalent of a calm, always-on second-pair-of-eyes on every single Pull Request, at near-zero marginal cost. It surfaces the same two categories of issue that most reliably damage software teams — security regressions and code-quality drift — but does so inline, at the point of change, with a one-click fix where possible, rather than as a wall of text the developer has to cross-reference against the diff themselves.

The Command Center summary gives a reviewer (or the PR author) a single number to anchor a merge decision on, plus a time-saved estimate that makes the tool's value legible to engineering leadership. Because the tone is deliberately calm rather than alarmist, the tool is designed to be read and trusted rather than dismissed as noise — shifting review effort from expensive human hours spent on mechanical checks to sub-cent-per-PR automation, without removing the human from the final merge decision.
